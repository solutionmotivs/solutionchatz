# Certificates: eFIRA, FIRC, eBRC, bank certificates, IRM: how they arrive automatically

Vaulte **never issues** these. They come from the authorised dealer bank, the licensed payout partner, DGFT (eBRC, via the exporter's bank) or RBI's EDPMS. Vaulte finds them, files them against the transfer, links them to the customer's request and tells the customer.

## Four ways a certificate arrives

| Source | How | Stored as | Needs |
|---|---|---|---|
| **Partner API poll** | Cron `POST /api/internal/documents/poll` (every 1-6 h, `CERT_POLL_INTERVAL_MIN`). For each completed India business transfer still missing an eFIRA/FIRC (and an eBRC for goods purposes P01xx) it asks the payout partner's `listDocuments`. | `source=POLL`, **VERIFIED** (the partner's own record over an authenticated call) | A partner adapter that implements `listDocuments`. Test mode: the mock partner. **No live adapter implements it yet**: partners' document endpoints are contract-specific (Wise and Airwallex do not issue eFIRA/eBRC; an Indian PA-CB partner would). Implement per contract. |
| **Partner webhook** | `document.available` event (signed, existing) | `source=PARTNER`, VERIFIED | Partner signing |
| **Inbound email** | Your mail forwarder (Resend/Postmark/Mailgun inbound, or a mailbox rule) POSTs each message to `POST /api/webhooks/inbound-email`, HMAC-signed with `INBOUND_EMAIL_SECRET` (`x-inbound-signature: sha256=<hex>`). Only senders on `INBOUND_EMAIL_SENDERS` (addresses or `@domain`) are accepted; empty list accepts nobody. The message is matched to **exactly one** transfer by a transfer id, partner reference or eFIRA number in the subject/body; the type is read from the subject/filename; PDF/PNG/JPEG only, judged by content. | `source=EMAIL`, **RECEIVED**: a staff member verifies it (never auto-verified) | Forwarder + secret + allow-list |
| **EDPMS / IRM CSV import** | Staff paste the bank's report in `/admin/documents`. Rows match by reference, else by amount + currency + date window when exactly one transfer fits. Ambiguous or unknown rows are listed, never guessed. | `source=RECONCILIATION`, VERIFIED (staff-imported, audited) | Staff |

Unmatched or ambiguous emails are queued for staff (`GET /api/admin/documents/inbound`); their attachments are not kept (no organisation to file them under), so the answer is to ask the sender to resend with the transfer reference.

When any source files a certificate, matching open customer requests close automatically and the requester is emailed (existing behaviour). Each transfer shows **when it was last checked and what the partner answered**.

## DGFT

I know of **no public DGFT or ICEGATE API through which a third party can pull a customer's eBRC**. eBRC is generated by the exporter's bank on the DGFT portal. So DGFT-originated eBRCs reach Vaulte as (1) the bank's/partner's email, (2) the partner API if the partner exposes it, (3) the EDPMS/eBRC report import. If DGFT or ICEGATE onboards you to a machine interface, add a `listDocuments`-style source behind its own environment variables; nothing in the product is hard-wired against that.

## What stays manual

Whether an eBRC is genuine and matches the shipping bill and IRM is a human check (status `RECEIVED` until staff verify). EDPMS closure itself is done by the customer's bank.
